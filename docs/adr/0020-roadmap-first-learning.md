# ADR 0020: Automatic, local-first learning roadmaps

Status: Implemented for review, 2026-10-06. Supersedes ADR 0014's learner-facing lifecycle and selection policy; its ownership, evidence, active-time and privacy rules remain.

The learner follows **Tu ruta de inglés**, with one current activity, completed history and upcoming steps. Onboarding automatically creates/activates a roadmap. `POST /api/v1/roadmap` ensures it for returning accounts and adapts upcoming steps. Both operations are authenticated and protected by CSRF/origin checks. Legacy plan proposal/accept/skip/refresh endpoints remain internal compatibility APIs; they have no learner navigation or controls.

`plan-v1` storage is retained with `plan-generator-v2` and `plan-catalog-v2`. The catalog adds fourteen adult everyday topics, from introductions through past experiences, travel, hotels, restaurants, shopping, relationships, work, hobbies, health, future plans, opinions and problem solving to free conversation. Selected A1–B2 is a learner preference, never an official assessment. Tutor prompts retain level scaffolding and Spanish help. Interests prioritize matching topics; canonical catalog order breaks ties. Topics in the last ten ended practices are placed behind less recent topics. Practice durations use the weekly goal's daily rhythm and retain the 2–10 minute bound.

Ollama's application-owned `PlanGenerator` port may select/reorder 2–5 **server candidate keys**. `roadmap-selection-v1` sends only level, interests, weekly minutes, recent topic names and safe candidate descriptions. It sends no account/profile/session/report/card IDs, learner quotes or authorization data. Model responses may contain only unique, allowed candidate keys, never activity definitions, types, scores or extra fields. Output is validated server-side; outage, timeout or malformed output uses the deterministic policy. There is no paid or cloud fallback. A three-second selection deadline and 256-token output limit bound local work. Recurring practices and short due reviews retain server priority; all safe conversation candidates fill the remaining progression rather than letting the model omit a topic permanently.

A signature of profile/goal versions, interests, recent topics and eligible candidate evidence detects meaningful changes. Provider work holds no account lock. The commit transaction rechecks the deletion epoch and fresh inputs; concurrent evidence edits use fresh deterministic candidates. Account serialization and existing partial unique indexes enforce one active roadmap. Repeated/concurrent ensure requests do not duplicate plans or activities. During adaptation completed and started activities retain their identity and order; only upcoming activities are regenerated. Completed route history remains completed when underlying sources expire, while unavailable evidence is redacted. Existing legacy plan reads retain their previous derived-completion behavior. New evidence for an already practised issue and newly due cards may create another short practice/review. A completed conversation cycle starts another cycle without erasing history.

The conversation-start defect was an optimistic-version check **before** the idempotency replay. A committed start incremented the plan version; retransmitting after a lost response failed with `STALE_PLAN_VERSION`. `started_from_version` is now stored in the session-link transaction, and its matching replay returns the same session before checking the new version. Unrelated stale mutations still fail. Roadmap starts enforce the current step. Sessions are fetched directly through an owned `GET /sessions/:id`, not located through the full history list. Browser starts have a synchronous duplicate-click guard, explicit inline failure and retry; reload resumes the stored link. A terminal empty session cannot strand the current step or manufacture completion. Successful linked ends and distinct target-card review events remain canonical completion evidence.

Leaving Home cancels the pending browser start and prevents late callbacks from reopening practice over another destination or logout. Cancellation does not erase a committed server link: returning to the route resumes that one session.

Roadmap vocabulary opens its assigned group of at most five owned, active, due cards rather than the general vocabulary queue. Partial reviews resume the remaining assigned cards. Finishing the group returns to the route automatically; other due cards cannot accidentally extend that step. The profile's vocabulary destination retains the general optional queue and suggestion controls.

Migration `202610060003_roadmap` adds ordering, start receipts and adaptation metadata and accepts both old/new generator/catalog versions. Backfill preserves the old slug order. Apply it before the new API; readiness checks migration/columns. It is additive and old backend SQL remains usable, but rolling back the UI reintroduces manual plan management. Do not down-migrate or remove privacy fences. The release identity names this migration and M11 as its previous compatible schema. No hosting/deployment or privacy pilot gate is changed.

Validation: all existing gates plus roadmap creation/ordering/start/advance/resume/adaptation/review/fallback/concurrency/ownership/privacy tests. Browser E2E exercises a real API with a deliberately unavailable local Ollama endpoint, as well as a committed start whose acknowledgement is dropped. `pnpm eval:ai -- --suite plans --billing-mode free_only` runs `roadmap-eval-v1` with six synthetic cases and adversarial validation. Optional `--live --max-calls 6` uses only local Ollama; no paid provider is supported. Educational usefulness and live model quality still require manual learner validation.
